# v0.8.2 HTML/CSS Compatibility Audit

Date: 2026-06-11

Historical note: this audit predates the hardened public authoring type surface. In current
authoring diagnostics, rejected props, style keys, and style values should be described as "not part
of the public authoring API". The word "unsupported" in this document is historical audit language
or projection fallback vocabulary unless a section explicitly discusses current diagnostics.

This audit treats `deckjsx`'s HTML-like JSX and CSS-like style API as a user-facing compatibility
promise. The current implementation is not just missing a few values; it mixes a slide-positioning
DSL with CSS-looking names. v0.8.2 should move the supported subset closer to HTML/CSS behavior
rather than requiring authors to add explicit layout parameters when defaults fail.

## Baseline References

- HTML rendering defaults are expressed in CSS terms, and user agents are expected to provide
  meaningful default rendering even when authors do not supply styles:
  <https://html.spec.whatwg.org/multipage/rendering.html>.
- CSS Display defines `display` with a broad grammar and initial value `inline`:
  <https://www.w3.org/TR/css-display-3/>.
- CSS Box Sizing defines `auto`, intrinsic sizes, and stretch-fit sizing rather than zero-size
  boxes for ordinary flow layout: <https://www.w3.org/TR/css-sizing-3/>.
- CSS Values and Units defines the broad length vocabulary, math functions, ratios, and CSS-wide
  keywords: <https://www.w3.org/TR/css-values-4/>.
- CSS Cascade defines defaulting and CSS-wide keywords such as `initial`, `inherit`, `unset`,
  `revert`, and `revert-layer`: <https://www.w3.org/TR/css-cascade-5/>.

## Findings

### High: block defaults are not HTML-like normal flow

Evidence:

- `ELEMENT_DEFAULTS.container` now defaults to `display: "block"` and CSS-like
  `position: "static"` in `src/style/defaults.ts`.
- `normalizeViewProps()` maps `display: "block"` to normal-flow block layout, while
  `position: "absolute"` remains the explicit opt-in for out-of-flow placement in
  `src/layout/normalization.ts`.
- Implemented in the current slice: `compileAbsoluteChildren()` now separates unpositioned block
  children into `compileBlockFlowChildren()`, while explicit absolute positioning remains local
  absolute placement. This keeps fixed-geometry authoring explicit without making ordinary block
  children overlap by default.

Why it matters:

HTML block elements create block boxes and participate in normal flow by default. A plain `<div><p>
...</p><p>...</p></div>` should not need explicit absolute coordinates to avoid zero frames or
overlap. Requiring explicit sizes is the wrong fix because it changes a broken default into an
authoring burden.

v0.8.2 action:

- Implemented in the current slice: `display: "block"` uses normal-flow block layout for
  unpositioned children.
- Implemented in the current slice: `position` is treated like CSS in the supported subset:
  `static` is normal flow, `relative` is normal flow plus visual offset, and `absolute` removes the
  element from flow.
- Implemented in the current slice: explicit `position: "absolute"` plus CSS positioning props remain
  the fixed-geometry authoring path.
- Implemented in the current slice: tests cover nested block text laying out vertically without
  explicit child size.

### High: `auto` and intrinsic sizing are mostly absent

Evidence:

- `DeckLength` excludes `auto`, `min-content`, `max-content`, `fit-content`, `calc()`, `min()`,
  `max()`, and `clamp()` in `src/style/types.ts`.
- `frameFromProps()` resolves unspecified sizes to `0` for absolute frames in
  `src/layout/absolute.ts`.
- Implemented in the current slice: simple text auto sizing gives block-flow text the available
  inline size and a line-height based block size. Wrapped text measurement is still not a general
  layout input.

Why it matters:

CSS uses `auto` and intrinsic sizing as core defaults. Missing width/height should not generally
mean `0`. It should mean "resolve from formatting context, available space, aspect ratio, or content
contribution".

v0.8.2 action:

- Implemented in the current slice: add a deckjsx-owned `auto` sizing model for the supported block
  subset.
- Implemented in the current slice: normal-flow block boxes and text stretch to available content
  width.
- Implemented in the current slice: text gets an intrinsic block size from registered TrueType
  metrics when available, with deterministic wrapped-line estimates as fallback. OpenType
  substitutions, mark positioning, UAX #9 mixed bidi ordering, and selected script segmentation now
  use replaceable deckjsx-owned boundaries; scripts outside that map and other unsupported shaping
  remain surfaced as fallback metadata.
- Implemented in the current slice: images use probed intrinsic dimensions and natural aspect ratio
  when one axis is provided. Intrinsic contribution to every layout mode remains future work.

### High: numeric length semantics are not CSS-like

Evidence:

- `DeckLength` accepts `number`; `parseLength()` resolves it as inches in `src/style/length.ts`.
- `DeckPointLength` accepts `number`; `parsePointValue()` resolves it as points in
  `src/style/length.ts`.
- `lineHeight` runtime code accepts a number as a multiple in `src/style/typography.ts`, but the
  public type is `DeckPointLength | "normal"` in `src/style/types.ts`.

Why it matters:

CSS permits unitless numbers only for specific properties. Most length properties require units,
with unitless `0` as the important exception. Today `width: 10`, `fontSize: 10`, and
`lineHeight: 10` have three different meanings across the API.

v0.8.2 action:

- Implemented in the current slice: classify numeric-accepting public style properties. Numeric
  domains such as `lineHeight`, `flexGrow`, `flexShrink`, opacity, order, ratios, and indices stay
  numeric; layout length numbers remain the documented deck legacy inches path; point-like text
  numbers remain points.
- Implemented in the current slice: keep CSS-like strings as the explicit CSS unit path for length
  properties, while documenting the legacy number convenience separately from CSS-compatible strings.
- Implemented in the current slice: `lineHeight` accepts unitless numbers as multipliers and tests
  cover the emitted percentage line spacing behavior.

### High: cascade/defaulting is incomplete

Evidence:

- v0.8.2 now accepts CSS-wide keywords on length-capable public style types and treats them as
  supported-subset defaults during projection, but full cascade-aware `inherit` / `unset` /
  `revert` semantics are still not implemented.
- Defaults are hard-coded by element kind in `src/style/defaults.ts`; there is no general
  property-level cascade/defaulting engine for inherited and reset values.
- Text run defaults repeat concrete `fontFamily`, `fontSize`, and `color` instead of inheriting from
  parent text context in `src/style/defaults.ts`.

Why it matters:

CSS-like styling is not just property names. Defaulting, inheritance, and reset keywords are part of
the mental model. Without them, `span`, nested text, theme defaults, and stylesheet overrides behave
like ad hoc merges.

v0.8.2 action:

- Implemented in the current slice: CSS-wide keywords on layout/text length-like properties no
  longer crash parsers or become explicit zero sizes. Projection falls back to the supported-subset
  initial/default behavior and records unsupported semantic metadata with
  `missing: ["cssWideKeywordCascade"]`.
- Implemented in the current slice: resolved styles inherit text-related values into inline
  `span` / text-run nodes while preserving parent text-box projection. Inherited properties include
  `color`, `font-family`, `font-size`, `font-weight`, `line-height`, `letter-spacing`, `direction`,
  text wrapping controls, and related text style values.
- Implemented in the current slice: element defaults behave as the default layer in the supported
  style resolution path, followed by theme defaults, stylesheet classes, and inline style. Full
  CSS reset keyword semantics remain future work and are diagnosed when authored.

### Medium: supported CSS value vocabulary is too narrow

Evidence:

- Length strings now support `in`, `cm`, `mm`, `Q`, `pt`, `pc`, `px`, `%`, `em`, `rem`, `vh`, `vw`,
  `vmin`, `vmax`, and `ch` in `src/style/types.ts` and `src/style/length.ts`.
- Missing CSS units still include `ex`, `cap`, `ic`, `lh`, `rlh`, and dynamic/small/large viewport
  units.
- No CSS math functions are parsed.

Why it matters:

The current type shape makes some CSS-looking values work and other standard CSS values fail for no
clear reason. `letterSpacing` was one example, but the same issue applies across length-capable
properties.

v0.8.2 action:

- Implemented in the current slice: add common absolute units (`cm`, `mm`, `Q`, `pc`) and safe
  viewport units (`vmin`, `vmax`) to the shared length/point parser, public types, stroke
  dasharray, and shadow length parsing.
- Implemented in the current slice: converge the length-capable properties touched by v0.8.2 on the
  shared parser, including layout lengths, point-like text values, stroke widths/dash arrays, and
  shadow lengths.
- Future v0.8.x: add `calc()`, `min()`, `max()`, and `clamp()` for lengths where the bases are
  known.
- Use one unsupported-value diagnostic path instead of silent fallback or unrelated writer errors.

### Medium: spacing shorthand is not CSS-compatible

Evidence:

- `Spacing` is either a scalar or exactly a four-item tuple in `src/style/types.ts`.
- `parseSpacing()` and `resolveBoxSpacing()` only expand scalar or four-value tuples in
  `src/layout/spacing.ts`.
- `margin` does not support `auto`.

Why it matters:

CSS authors expect `padding: "8px 16px"`, `margin: "1em 0 2em"`, and `margin: "0 auto"` to work.
The current tuple-only API is convenient for TypeScript but not CSS-like.

v0.8.2 action:

- Implemented in the current slice: support CSS 1/2/3/4-value spacing shorthand strings.
- Implemented in the current slice: diagnose unsupported `auto` margins explicitly and use a zero
  fallback so projection continues. Full CSS auto-margin distribution remains future work.
- Keep tuple authoring as a deckjsx convenience, but do not let it define the CSS-like contract.

### Medium: HTML element surface is much narrower than the naming suggests

Evidence:

- Authored tags are limited to sectioning/view tags, `h1`-`h6`, `p`, `img`, `shape`, and `span` in
  `src/authoring/tags.ts`.
- Public props expose `style`, `className`, `area`, image source fields, and shape kind only in
  `src/authoring/props.ts`.
- There is no `ul`, `ol`, `li`, `a`, `br`, `hr`, `video`, `audio`, table, or form surface.

Why it matters:

This is acceptable as a typed subset, but it must be explicit. The missing tags also affect CSS
defaults: headings, paragraphs, lists, images, and inline elements each have UA-style expectations.

v0.8.2 action:

- Implemented in the current slice: document the supported intrinsic tag subset as the compatibility
  target.
- Implemented in the current slice: keep UA-like readable defaults for currently supported text-like
  tags while documenting deck-specific defaults such as shape fill and box sizing.
- Keep `video` out of v0.8.2 per release scope, but reserve the authoring/model shape for v0.8.3.

### Medium: selectors are a useful subset but not CSS selector parity

Evidence:

- Selectors support authored tag names, class selectors, compound tag/class selectors, and descendant
  selectors in `src/style/selectors.ts`.
- No ID selectors, attribute selectors, pseudo-classes, pseudo-elements, child/sibling combinators,
  selector lists, or nesting are supported.

Why it matters:

The subset is reasonable, but unsupported selector syntax must not be silently ignored in a way that
looks like a CSS cascade bug.

v0.8.2 action:

- Implemented before and retained in this slice: keep the selector subset and return diagnostics for
  unsupported selector syntax.
- Implemented before and retained in this slice: tests prove source order and specificity match CSS
  for the supported selector subset.
- Implemented in docs: avoid saying "CSS selectors" without "supported subset".

### Medium: flex and grid are partial CSS analogs

Evidence:

- `CssFlexDirection` only supports `row` and `column`; no reverse directions in `src/style/types.ts`.
- Flex shorthand is absent; `flexBasis` is only `DeckLength | "auto"`.
- Grid supports templates, `fr`, `minmax()`, repeat forms, areas, and auto placement, but not full CSS
  track sizing keywords or named line behavior.

Why it matters:

Flex/grid are the best path for ergonomic deck layout, but defaults must match CSS where names match.
If `display: "flex"` means CSS flex, row direction and stretch defaults should hold consistently.

v0.8.2 action:

- Implemented in the current slice: finish CSS-like flex defaults for row/column, stretch, gap axes,
  and flex basis auto behavior in the supported subset.
- Implemented in the current slice: add diagnostics for unsupported common values like
  `row-reverse`, `column-reverse`, `wrap-reverse`, plus unsupported CSS-like style-property warnings
  for `flex` and `flexFlow` when they arrive via JavaScript or unsafe casts.
- Implemented in docs: document grid default tracks as deck-specific where they differ from browser
  implicit `auto` tracks.

### Medium: images have useful controls but the model is fragmented

Evidence:

- `ImageStyle` supports `fit`, `objectFit`, `objectPosition`, `crop`, and image effects in
  `src/style/types.ts`.
- Implemented in the current slice: `objectFit: "fill"` is accepted as the CSS spelling for the
  existing `stretch` projection. CSS `object-fit` also has `none` and `scale-down`, which still
  require natural-size comparison and are not implemented.
- Background images use separate `backgroundSize`, `backgroundPosition`, `backgroundRepeat`,
  `backgroundClip`, and `backgroundOrigin` paths in `src/style/background.ts`.

Why it matters:

Authors think in one image-positioning model: natural size, aspect ratio, cover/contain, focal point,
crop, and alignment. `img` and `background-image` currently expose adjacent but different vocabularies.

v0.8.2 action:

- Implemented in the current slice: align `objectFit` vocabulary with CSS by accepting `fill` as an
  alias for `stretch`.
- Implemented in the current slice: keep `objectPosition` parsing and diagnostics consistent across
  foreground images and background layers for the supported subset.
- Implemented in the current slice: add examples/tests for natural aspect ratio, cover/focal-point
  positioning, contain-style alignment, and manual crop.

### Medium: colors, borders, backgrounds, and transforms are partial

Evidence:

- Colors support named colors, hex, rgb/rgba, hsl/hsla, and transparent in `src/style/color.ts`, but
  not `currentColor`, system colors, `hwb()`, Lab/LCH/OKLab/OKLCH, relative colors, or
  `color-mix()`.
- Border shorthand parses width/style/color but supports only none/solid/dash/dotted-style mapping
  in `src/style/stroke.ts`.
- `borderRadius` is a single length rather than CSS 1-4 corner radii plus slash syntax.
- `parseBackgroundShorthand()` only extracts a color from `background` in
  `src/style/background.ts`.
- Transforms support common 2D functions, but not 3D transforms or all CSS transform-adjacent
  properties.

Why it matters:

These are not just "nice to have"; they are areas where authored CSS-looking strings can currently
be silently reduced or preserved as unsupported semantics.

v0.8.2 action:

- Implemented in the current slice: prefer explicit unsupported-semantic diagnostics for valid CSS
  that deckjsx cannot project in the v0.8.2 focus areas.
- Implemented in the current slice: tighten high-use shorthands and values already exposed in the
  API, including spacing, border radius percentages, border/stroke length units, and shadow spread
  fallback metadata.
- Future v0.8.x: expand heavier paint parity such as full `background` shorthand, multi-corner
  `border-radius`, `currentColor`, and broader color functions.

## Second-Pass Property Gaps

The first pass identified the broad incompatibility: deckjsx defaults are often absolute-layout
defaults, not CSS defaults. A second pass over `src/style`, `src/layout`, and the PPTX projection
found additional property-level differences that should be tracked for v0.8.2.

### High: percentage bases are inconsistent or missing

Evidence:

- `parseSpacing()` resolves scalar and tuple spacing with `parseLength(value, 0, 0, context)` in
  `src/layout/spacing.ts`.
- `resolveMainGap()` and `resolveCrossGap()` also resolve `gap`, `rowGap`, and `columnGap` against
  a `0` base in `src/layout/stack.ts`.
- CSS Box Model defines `padding` as a one-to-four-value shorthand whose percentages refer to the
  containing block's logical width. CSS gap percentages also have layout-specific bases rather than a
  universal zero base.

Why it matters:

CSS authors expect `padding: "10%"`, `margin: "5%"`, and percentage gaps to resolve against a real
container dimension. In deckjsx these values can collapse to `0`, producing layout that looks like a
parser accepted the value but ignored the intended size.

v0.8.2 action:

- Implemented in the current slice: give spacing and gap resolution real property-specific
  percentage bases.
- Implemented in the current slice: add tests for percentage `padding`, `margin`, `inset`, `gap`,
  `rowGap`, and `columnGap`.
- If a base is unavailable, emit an unsupported-value diagnostic rather than silently resolving to
  `0`.

### High: position and inset are not CSS positioned layout

Evidence:

- `CssPosition` supports `"static" | "absolute" | "relative"` in `src/style/types.ts`; CSS also has
  `fixed` and `sticky`.
- `top`, `right`, `bottom`, `left`, and `inset` accept only `DeckLength`-like values; `auto` and
  logical insets are absent.
- Historical `x` and `y` frame coordinates are not part of public CSS-like element style.
- In `src/layout/absolute.ts`, missing insets and sizes often fall back to the parent's origin and
  zero size rather than CSS static-position and auto-size rules.

Why it matters:

CSS absolute positioning is intentionally out-of-flow, while normal layout is the default. deckjsx
currently makes local absolute positioning feel like the default for block containers, which reverses
that mental model.

v0.8.2 action:

- Keep `static` as the default conceptual position for CSS-like layout.
- Implemented in the current slice: define `relative` as normal-flow layout plus visual offset, not
  as "mostly in flow".
- Implemented in the current slice: diagnose unsupported `auto` insets explicitly and treat them as
  unspecified in the fallback layout instead of failing length parsing.
- Remove `x`/`y` from the public authoring API. Runtime inputs that still contain these keys should
  produce authoring diagnostics instead of being treated as compatibility aliases.

### High: writing mode and direction do not drive layout axes

Evidence:

- `writingMode` and `direction` exist on `TextStyle` and `TextRunStyle` in `src/style/types.ts`.
- `resolveTextDirection()` maps text-body writing mode to PPTX text direction in
  `src/style/typography.ts`.
- Stack, grid, spacing, inset, and alignment code resolve physical axes and do not use writing mode
  or direction to map inline/block starts.

Why it matters:

In CSS, writing mode and direction affect inline/block axes, text flow, logical properties, and some
alignment behavior. In deckjsx they are mostly text rendering metadata. That is acceptable only if
logical CSS properties are clearly out of scope; otherwise values like `start`, `end`, percentage
padding, and object positioning can disagree with CSS expectations.

v0.8.2 action:

- Implemented in the current slice: define v0.8.2 as a physical-axis layout subset where
  `writingMode` and `direction` project to PPTX text-body direction but do not remap layout axes.
- Implemented in the current slice: add diagnostics for `writingMode` and `direction` being text-body
  projection only. Text nodes preserve PPTX text-body direction while recording that logical layout
  axes and logical start/end mapping are missing.
- Do not market `start`/`end` alignment as fully logical until direction and writing mode participate
  in layout.

### Medium: display values and generated box behavior are incomplete

Evidence:

- `CssDisplay` is only `"flex" | "block" | "grid" | "none"` in `src/style/types.ts`.
- CSS Display has inner/outer display concepts and values such as `inline`, `inline-block`,
  `inline-flex`, `inline-grid`, `flow-root`, `list-item`, `contents`, table values, and legacy
  combined values.
- `span` is a text run only inside text content; there is no inline layout model for arbitrary inline
  boxes.

Why it matters:

Many CSS defaults depend on whether a box is inline, block, list-item, replaced, or display-none.
The current subset can be fine, but `display: "block"` must not imply absolute positioning, and
unsupported display values need diagnostics instead of TypeScript-only absence.

v0.8.2 action:

- Treat the v0.8.2 display subset as `block`, `flex`, `grid`, and `none`.
- Implemented in the current slice: implement unpositioned block children as normal flow.
- Implemented in the current slice: emit projected `layout` unsupported semantics for unsupported
  valid CSS display values seen from JavaScript or unsafe casts.
- Reserve `inline` and `inline-block` for a later inline layout slice unless `span` grows beyond text
  runs.

### Medium: overflow and visibility are only partial paint filters

Evidence:

- `CssOverflow` supports only `visible` and `hidden`; CSS also defines `clip`, `scroll`, and `auto`
  in CSS Overflow.
- `overflow: "hidden"` intersects with an axis-aligned clip rect in `src/layout/resolve.ts`.
- `CssVisibility` supports `visible` and `hidden`; CSS visibility is inherited and has additional
  table-related `collapse` behavior.

Why it matters:

`overflow: auto`/`scroll` cannot be faithfully represented in PPTX, but accepting only `hidden` and
`visible` leaves common CSS values with no clear behavior. Visibility should also be resolved through
inheritance/defaulting rather than independent hard-coded element defaults.

v0.8.2 action:

- Implemented in the current slice: add projected `layout` unsupported semantics for
  valid-but-unprojectable overflow values (`auto`, `scroll`, `clip`).
- Keep the current axis-aligned clipping fallback, but report transformed clipping as approximate.
- Implemented in docs: `visibility` remains a per-node projection flag in v0.8.2 rather than full
  inherited CSS visibility.

### Medium: alignment grammar is narrower than CSS Box Alignment

Evidence:

- `CssAlignItems`, `CssAlignSelf`, `CssJustifyContent`, and `CssAlignContent` accept only a small
  keyword subset in `src/style/types.ts`.
- `parsePlaceSelf()`, `parsePlaceItems()`, and `parsePlaceContent()` split simple tokens and ignore
  richer grammar such as baseline alignment and safe/unsafe overflow-position keywords in
  `src/layout/normalization.ts`.
- CSS Box Alignment defines `place-items`, `place-self`, `place-content`, default alignment, gap
  properties, overflow-position keywords, and baseline/self-position/content-position families.

Why it matters:

`start`, `end`, and `stretch` are not just synonyms for physical coordinates in CSS. They depend on
layout mode, direction, writing mode, baseline participation, and overflow safety.

v0.8.2 action:

- Implemented in the current slice: diagnose unsupported alignment grammar through projected
  `layout` unsupported semantics, including `normal`, baseline, safe/unsafe, self-start, and
  self-end forms.
- Implemented in the current slice: preserve unsupported `place-*` grammar as fallback metadata
  rather than only partially applying supported tokens and dropping the rest.
- Implemented in the current slice: add tests for unsupported alignment grammar from JavaScript
  inputs.

### Medium: flex accepts only selected longhands

Evidence:

- `flexDirection` omits `row-reverse` and `column-reverse`; `flexWrap` omits `wrap-reverse`.
- There is no `flex` or `flex-flow` shorthand in `src/style/types.ts`.
- CSS flex defines `flex-direction`, `flex-wrap`, `flex-flow`, `flex`, `flex-grow`,
  `flex-shrink`, and `flex-basis`, with `flex` initial `0 1 auto`.

Why it matters:

Deck authors will naturally try common CSS flex shorthand such as `flex: 1`, `flexFlow: "row wrap"`,
or `flexDirection: "row-reverse"`. Today the supported model is close enough to CSS to invite those
inputs but not broad enough to handle or diagnose them consistently.

v0.8.2 action:

- Implemented in the current slice: explicitly diagnose `row-reverse`, `column-reverse`, and
  `wrap-reverse` through projected `layout` unsupported semantics.
- Implemented in the current slice: diagnose `flex` / `flexFlow` as unsupported CSS-like style
  property names when they arrive through JavaScript or unsafe casts. Full shorthand parsing remains
  future work.
- Keep `layout: "stack"` as the deck-specific spelling and `display: "flex"` as the CSS-like
  spelling.

### Medium: grid placement silently loses named-line and auto semantics

Evidence:

- `CssGridLine` is `number | "auto" | \`span ${number}\``; named lines are unsupported.
- `parseGridPlacement()` uses `Number.parseInt()` and clamps starts/spans to positive numbers in
  `src/layout/grid.ts`.
- `parseGridAreaShorthand()` only handles slash placement, while non-slash named areas are carried
  through `gridArea` elsewhere.
- CSS Grid supports named lines, negative line indexes, `auto`, named areas, `span <custom-ident>`,
  and a richer track sizing grammar.

Why it matters:

Grid is currently the most CSS-like layout surface in deckjsx, so silent simplification is risky.
Inputs such as `gridColumn: "content-start / content-end"` or negative line numbers should not parse
as accidental positive lines or disappear.

v0.8.2 action:

- Implemented in the current slice: add projected `layout` unsupported semantics for named-line,
  negative-line, and unsupported span grammar.
- Avoid `parseInt()` fallbacks that turn invalid CSS into line `1`.
- Implemented in the current slice: add tests for invalid/unsupported grid placement strings.

### Medium: background defaults and shorthand differ from CSS

Evidence:

- `resolveBackgroundImageSizing()` defaults missing `backgroundSize` to `fit: "stretch"` in
  `src/style/background.ts`; CSS background-size initial is `auto auto`.
- `resolveBackgroundImageRepeat()` defaults to `no-repeat`; CSS background-repeat initial is
  `repeat`.
- The code supports useful background layers and gradients, but not the full CSS background
  shorthand grammar, `background-attachment`, or all background-repeat two-keyword forms.

Why it matters:

This is presentation-friendly, but it is not CSS. A CSS author expects repeated, natural-size
backgrounds unless they say otherwise. Deck authors may prefer cover/stretch defaults, but then the
public contract should not imply browser CSS defaults.

v0.8.2 action:

- Implemented in docs: document that element and slide background defaults remain
  presentation-oriented in v0.8.2 rather than CSS initial values.
- Future v0.8.x: decide whether element backgrounds should switch to CSS initial behavior while
  slide backgrounds keep presentation defaults, or whether explicit deck-specific presets should
  carry presentation defaults.
- Existing background parser diagnostics remain the fallback path for unsupported background
  components; fuller background shorthand parity is future work.

### Medium: shadows are a lossy subset

Evidence:

- `parseShadowShorthand()` supports one shadow layer only in `src/style/shadow.ts`.
- Shadow lengths now share the point-length parser, including absolute CSS units and safe viewport
  units, but percentages and CSS math are not accepted.
- Spread radius is accepted as the fourth CSS length and projected as unsupported fallback metadata
  because `ShadowIR` and the current PPTX writer do not reproduce CSS spread geometry.

Why it matters:

CSS-like `boxShadow` and `textShadow` are often copied directly from web CSS. Ignoring spread or
additional layers changes visual meaning while appearing to accept the declaration.

v0.8.2 action:

- Implemented in the current slice: emit unsupported-semantic diagnostics for spread radius while
  preserving the projected offset/blur/color shadow fallback.
- Existing behavior already diagnoses multiple layers and unsupported tokens. Text-shadow-specific
  semantic differences remain a follow-up diagnostic target.

### Medium: text properties are projection hints, not CSS text layout

Evidence:

- `whiteSpace`, `wordBreak`, and `overflowWrap` resolve to a boolean `wrap` in
  `src/style/typography.ts`.
- `textDecoration` only influences underline and line-through booleans; decoration thickness,
  skip-ink, multi-line details, and overline are absent.
- `textTransform: "capitalize"` uses a regex-based transformation in `src/style/typography.ts`, not
  CSS's full language-sensitive text-transform behavior.
- `verticalAlign` accepts `top | middle | bottom`, while CSS vertical-align has baseline/sub/super
  and length/percentage forms for inline/table contexts.

Why it matters:

Text layout is where CSS compatibility expectations are strongest. Collapsing line-breaking and
white-space behavior into a single wrap boolean loses important semantics such as preserved spaces,
newlines, break opportunities, and intrinsic size contributions.

v0.8.2 action:

- Implemented in the current slice: keep the boolean PPTX wrap projection while preserving authored
  text-layout semantics in inspection and using deterministic wrapped-line estimates for auto-height;
  the missing font-specific metrics and shaping are retained as fallback metadata.
- Existing tests cover the supported `whiteSpace`, `overflowWrap`, and `wordBreak` aliases as a PPTX
  wrap subset.
- Future v0.8.x: add richer diagnostics for unsupported `textDecoration` parts, `verticalAlign` CSS
  values, and exact white-space preservation semantics.

### Low: CSS declaration semantics are not CSS parser semantics

Evidence:

- Styles are JavaScript objects, not CSS text declarations. There is no support for `!important`,
  custom properties, `var()`, comments, duplicate declarations, declaration order inside one style
  block, or invalid-declaration recovery.
- Style resolution merges default, theme, class, and inline layers by object properties in
  `src/style/resolve.ts`.

Why it matters:

This is a reasonable TypeScript-first API, but it means "CSS-like" should mean CSS value/layout
semantics for supported properties, not full CSS stylesheet parsing.

v0.8.2 action:

- Document that style objects are the authoring syntax.
- Implemented in the current slice: add CSS-compatible value parsing where v0.8.2-supported
  properties accept CSS-looking strings.
- Avoid adding broad strings that look like CSS but cannot be validated.

## Third-Pass Property Gaps

This pass focused on places where a CSS author may reasonably try a standard property spelling that
is not present in the current public style key set, or where a supported property still accepts only
a presentation-oriented subset.

### Medium: missing CSS property spellings can disappear before diagnostics

Evidence:

- Authored inline styles are captured by `mergedAuthoredStyle()` as object entries, but theme
  validation and typed style keys are limited to the keys exported from `src/style/types.ts`.
- The supported key set does not include common CSS shorthands and logical properties such as
  `flex`, `flexFlow`, `inlineSize`, `blockSize`, `minInlineSize`, `maxInlineSize`,
  `marginInline`, `marginBlock`, `paddingInline`, `paddingBlock`, `insetInline`, `insetBlock`,
  `borderBlock`, `borderInline`, or `textDecorationThickness`.
- Because these keys are not first-class `StyleDeclaration` keys, TypeScript users cannot author
  them without unsafe casts, and runtime diagnostics are inconsistent compared with unsupported
  values on known keys.

Why it matters:

CSS compatibility is not only value parsing. If a common CSS property spelling is silently ignored
or never reaches the unsupported-semantic path, users see a styling bug rather than a clear subset
boundary.

v0.8.2 action:

- Implemented in the current slice: keep the current key subset for projection, but emit
  nonblocking compile warnings for unsupported CSS-like style property names while preserving the
  authored style in the graph for inspection.
- Implemented in the current slice: unknown style-key diagnostics cover cases such as `flex`,
  `flexFlow`, and logical sizing/spacing keys when they arrive from JavaScript or unsafe casts.
- Do not claim broad CSS property support from the existence of a JavaScript `style` prop.

### Medium: aspect-ratio and object-fit now have CSS aliases, but not full CSS behavior

Evidence:

- Implemented in the current slice: `aspectRatio: "auto"` is accepted and treated as no authored
  ratio, matching the CSS initial-value use case.
- Implemented in the current slice: string numeric ratios such as `aspectRatio: "1.5"` are accepted
  in addition to numeric ratios and `"16 / 9"` forms.
- Implemented in the current slice: `objectFit: "fill"` aliases to the existing `stretch`
  projection.
- CSS `object-fit: none` and `scale-down` still require natural-size comparison and a decision about
  whether the image box or source rectangle should preserve unscaled pixels in PPTX.

Why it matters:

These are high-friction porting cases from web CSS. Supporting the safe aliases removes accidental
syntax failures, while documenting `none` / `scale-down` prevents over-promising browser image
layout.

v0.8.2 action:

- Keep `fill` and `auto` as supported aliases in v0.8.2.
- Implemented in the current slice: diagnose `object-fit: none` and `scale-down` when unsafe-cast
  values reach projection, preserving the authored value and falling back to `contain` instead of
  emitting an invalid PPTX image fit. Exact natural-size projection remains a future image sizing
  slice.
- Keep `stretch` as the deckjsx/PPTX-friendly alias for authors who think in slide geometry rather
  than CSS.

### Medium: inherited CSS properties are only a text-run subset

Evidence:

- `INHERITED_STYLE_KEYS` in `src/style/resolve.ts` covers text-related properties such as `color`,
  `fontFamily`, `fontSize`, `lineHeight`, `letterSpacing`, `direction`, `whiteSpace`, `wordBreak`,
  and `overflowWrap`.
- CSS inherited properties also include values not modeled or not inherited here, such as
  `visibility`, `cursor`, `quotes`, many font-variant properties, and richer writing/line-breaking
  controls.

Why it matters:

The implemented inheritance fixes the most visible `span` / rich text behavior, but it is not a full
CSS inheritance engine. Reset keywords like `inherit` and `unset` still cannot be exact without
property-level inherited/non-inherited classification.

v0.8.2 action:

- Document the inherited subset as "text-run inheritance", not full CSS inheritance.
- Keep CSS-wide keyword diagnostics for full reset/cascade semantics.
- If `visibility` inheritance is needed for author expectations, implement it as a separate
  projection flag decision rather than folding it into rich text inheritance accidentally.

## Fourth-Pass Property Inventory

This pass looked for standard CSS settings that are easy to paste into a JavaScript `style` object
but are not first-class deckjsx properties yet. The v0.8.2 rule is: known deckjsx keys should either
behave like the supported CSS subset or produce projected unsupported semantics; unknown CSS-like
keys should produce compile warnings instead of disappearing.

### Medium: logical property families need a documented boundary

Evidence:

- Current runtime warnings catch unknown keys such as `marginInline`, but CSS logical properties are
  a family: `inlineSize`, `blockSize`, `insetInlineStart`, `paddingBlockEnd`,
  `borderInlineStartWidth`, `borderStartStartRadius`, and related longhands.
- v0.8.2 layout intentionally resolves physical axes; `writingMode` and `direction` do not remap
  spacing, insets, grid, flex, or object positioning.

v0.8.2 action:

- Implemented in the current slice: unsupported CSS-like property-name warnings are broad enough to
  catch these keys when they arrive through JavaScript or unsafe casts.
- Document this as a physical-axis subset. Do not alias logical properties to physical ones in
  v0.8.2, because that would be wrong for RTL and vertical writing modes.

### Medium: paint shorthands are intentionally shallow

Evidence:

- `background` extracts only a color while `backgroundImage`, `backgroundSize`,
  `backgroundPosition`, `backgroundRepeat`, `backgroundClip`, and `backgroundOrigin` are separate
  deckjsx inputs.
- `borderRadius` is a single radius; CSS corner longhands, multi-value radii, and slash syntax are
  not modeled.
- `outline` and `border` support common width/style/color cases, but not the full CSS border image,
  radius, or outline-offset family.

v0.8.2 action:

- Keep these as explicit future paint-parity items. The v0.8.2 requirement is diagnostics/fallbacks
  for known unsupported authored values, not a full CSS parser for every paint shorthand.
- Compile warnings cover property spellings such as `backgroundAttachment`, `backgroundBlendMode`,
  `borderTopLeftRadius`, `outlineOffset`, and `boxDecorationBreak` when they appear at runtime.

### Medium: font and text families are richer than the current PPTX projection

Evidence:

- deckjsx supports common text projection values such as `fontFamily`, `fontSize`, `fontWeight`,
  `fontStyle`, `textDecoration*`, `textTransform`, `whiteSpace`, `wordBreak`, and `overflowWrap`.
- CSS font/text also includes `font`, `fontVariant*`, `fontStretch`, `fontKerning`,
  `fontFeatureSettings`, `fontVariationSettings`, `textOverflow`, `textWrap`, `hyphens`,
  `lineBreak`, and `tabSize`.

v0.8.2 action:

- Keep the supported text subset focused on PPTX-projected properties and text-run inheritance.
- Compile warnings cover unsupported CSS-like spellings from JavaScript inputs; richer text layout
  and font-feature projection remain future work.

## v0.8.2 Implementation Order

1. Define the supported HTML/CSS subset as a compatibility contract, not a list of surprises.
2. Implement CSS-like defaulting/cascade foundations: inherited text properties, CSS-wide keyword
   policy, and UA-like tag defaults for supported tags. Current slice implements CSS-wide keyword
   parser fallbacks and diagnostics for layout/text length-like properties plus text-run inheritance;
   full reset semantics remain.
3. Implemented in the current slice: normal-flow block layout for unpositioned block children,
   including non-zero text auto frames.
4. Normalize numeric, unit, percentage-base, and `auto` handling across all CSS-like properties. The
   current slice adds common CSS absolute units, `vmin`/`vmax`, percentage bases for spacing/gaps,
   `aspectRatio: "auto"`, and `objectFit: "fill"`; CSS math and remaining relative units are still
   follow-up work.
5. Expand spacing, length, aspect-ratio, object-fit/object-position, background, and image intrinsic
   sizing. Current slice covers spacing shorthands, foreground image natural aspect ratio, safe
   object-fit/aspect-ratio aliases, and object-position diagnostics.
6. Add diagnostics for unsupported valid CSS values/selectors rather than silent fallback. The
   current slice covers layout projection diagnostics for display, overflow, position, flex
   direction/wrap, alignment grammar, grid placement, auto inset/margin fallback, logical text-axis
   limitations, CSS-wide keyword fallback, and compile-time warnings for unsupported CSS-like style
   property names.
7. Add focused tests for percentage spacing/gaps, position/inset, writing-mode limitations,
   unsupported alignment grammar, flex/grid unsupported grammar, and shadow lossiness. Current slice
   includes shadow spread fallback diagnostics.
8. Update README, skill docs, and examples only after the implementation behavior is no longer an
   explicit-size workaround.

## Explicit Non-Goal

v0.8.2 does not need full browser parity. It does need honest CSS-compatible behavior for the subset
that deckjsx exposes with CSS names. The safe rule is:

- If deckjsx supports a CSS property/value spelling, it should behave like CSS unless clearly named as
  a deck-specific extension.
- If deckjsx cannot support that CSS behavior yet, it should reject or diagnose the unsupported
  meaning rather than require authors to add unrelated layout parameters.
