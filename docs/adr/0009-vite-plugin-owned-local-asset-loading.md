# Vite plugin owns project-local asset loading

deckjsx core keeps the Asset Loading Boundary runtime-neutral: built-in handling may cover inline bytes, data sources, and fetchable absolute URLs, but relative paths and local file sources require an explicit AssetLoader. Project-local default asset loading will live in integration packages, starting with a monorepo plugin package shaped like `plugins/vite` and published as `@deckjsx/vite`, so Node filesystem access, project-root resolution, and bundler module-graph behavior do not become dependencies or hidden assumptions of the core authoring, Project, or Render pipeline.

Core built-in asset handling should stay narrow: already-provided bytes, data/data URI sources, and absolute HTTP(S) URL sources when the runtime provides `fetch`. Core built-in handling should not interpret relative paths, root-absolute project paths, `file:` URLs, Vite public-directory assets, or local filesystem paths. If an absolute URL needs built-in fetching but `fetch` is unavailable, Project should surface an Asset Loading Boundary diagnostic through the existing probe diagnostics because Project-time image metadata cannot be completed. HTTP non-2xx responses and network failures should also become Project-time Asset Loading Boundary diagnostics rather than thrown exceptions for expected user-manageable external asset problems. It should not fall through to path or Node behavior.

When built-in URL fetch succeeds during Project, core should retain both probe metadata and fetched bytes on the Asset Artifact so Render embeds the same bytes without fetching the URL again. Built-in URL provenance should use `kind: "fetch"`, `resolverIdentity: "deckjsx:builtin"`, and a bytes-derived hash source when core computed the hash from fetched bytes.

Filesystem-like paths remain valid core Authored Media Sources. The restriction is that core preserves and validates those sources but does not resolve them; a Project Integration Package or Runtime Integration Package supplies the AssetLoader that interprets the path.

The target package boundary is that the core `deckjsx` package does not import `node:*` modules. The current thin Node output runtime boundary should be removed from core in v0.8.5 rather than carried as a transitional compatibility layer, while core continues to expose runtime-neutral artifacts and maintain internal loader seams for future integration packages.

This separation is specifically about runtime compatibility, not only dependency tidiness: `node:fs` and related Node APIs do not exist in Edge runtimes and similar non-Node environments, so core should not make them unavoidable for users who only need to author, Project, Render to bytes, or supply their own runtime-safe asset loaders.

The package split should distinguish project-toolchain integration from runtime integration. A Vite package, shaped like `@deckjsx/vite`, owns Vite project graph behavior and Vite-aware default asset loading. A Node runtime package, shaped like `@deckjsx/node` or `@deckjsx/runtime-node`, owns path output and reusable local file AssetLoader primitives. The Vite package may use the Node runtime package when running in Node, but Node filesystem behavior should not be defined as Vite-specific behavior.

This decision also sets the v0.8.5 direction for core Render: core should render to runtime-neutral artifact bytes and remove the root/core `output: string` file-writing option. Path output belongs to a future Node Runtime Integration Package. Because this project is pre-1.0 and the HMR compatibility line has not been reached, preserving a deprecated core `output: string` compatibility path would only keep the Node runtime dependency alive in the wrong package. The same removal applies to the current internal Node output modules and public output side-effect types: v0.8.5 should delete the core Node output implementation rather than leave unused `WrittenOutput` or `RenderOutputSideEffect*` concepts in core.

Relative media path resolution needs an origin-bearing loader context. The core AssetLoader contract should be able to pass Media Source Origin, such as a source identity and importer/module id, to loaders. This origin is integration-supplied metadata, not an everyday `deck.slide()` authoring option users are expected to write by hand. Core provides this origin as data; `@deckjsx/vite` interprets it with the Vite module graph and project root, while core remains unaware of Vite and Node filesystem APIs.

Media Source Origin should carry `sourceIdentity` for deckjsx pipeline explanation and `importer` as an optional string for project-toolchain resolution. `sourceIdentity` connects the asset back to deckjsx composition identity; `importer` gives integrations such as `@deckjsx/vite` the module id used to resolve relative media paths. `importer` is not constrained to an absolute filesystem path, because Vite and other integrations may use virtual ids or plugin-resolved ids. Core stores and passes the string but does not interpret it.

When hidden media-origin metadata is absent, graph construction should fall back to the current semantic Source Origin by preserving `sourceIdentity` for mounted sources and leaving `importer` undefined. Root sources do not need a synthetic source identity string. A relative path with no importer remains a loader-level problem that should surface through handled-failure diagnostics when a loader claims it.

Media Source Origin should be captured on the Asset Entity created from an authoring media source prop. AssetLoaderContext receives the authored source plus that Asset Entity's captured origin, so probing and loading use the same origin without requiring PPTX projection or Render to rediscover the source module.

AssetLoaderContext should also carry `assetEntityId` and required `sourceField` alongside `source`, optional `origin`, and `resolverIdentity`. `assetEntityId` and `sourceField` are for diagnostics, tracing, and inspection; they should not replace Resolver Identity or become cache identity. This lets a loader explain failures differently for `video.src` and `video.poster` even when the authored path string is the same. `origin` is optional because inline data fields and root sources may not need or have module-origin metadata. If a path source reaches an integration loader without the origin/importer data that loader needs, the loader should return an `ok: false` diagnostic rather than core inventing a synthetic origin.

The user-facing authoring shape stays `src`/`data` media props. Extra information needed to interpret a relative `src` is attached internally by the integration or source registration plumbing, then passed to the AssetLoader context; it should not appear as a second public media prop or required slide option.

The initial integration can attach Media Source Origin at source or slide-factory granularity. The internal model should still allow prop-level origin override so JSX fragments or components imported from another module can resolve their own relative media references against the module that authored each media prop instead of the module that happened to render them.

For component-authored literal media references, the component's defining module is the Media Source Origin. For example, `<img src="./logo.png" />` inside `components/Logo.tsx` resolves relative to `components/Logo.tsx`, even when `<Logo />` is rendered by `slides/Intro.tsx`.

For prop-authored media references, the module that authored the prop value remains the Media Source Origin. For example, `<Logo src="./customer-logo.png" />` inside `slides/Intro.tsx` resolves relative to `slides/Intro.tsx` even if `Logo` forwards that prop to `<img src={props.src} />` from `components/Logo.tsx`.

Media Source Origin should be attached when a JSX prop is assigned, not by wrapping or branding the string value itself. A Vite transform or internal helper can attach origin metadata to the `src` or `poster` prop position, and component prop forwarding should preserve that prop-level metadata when the value is forwarded to an intrinsic media element. This keeps authored `src` and `poster` values as ordinary strings.

Arbitrary component props should remain ordinary TypeScript props and should not expose a public `MediaSource<T>` wrapper, branded string, or origin-aware prop type. The JSX runtime and Author Tree can preserve origin metadata internally while component code sees and forwards normal string values. Because function components do not become Author Tree nodes themselves, component prop forwarding needs an internal JSX runtime props metadata carrier. That carrier moves prop-level origin metadata through function component calls and writes it onto intrinsic Author Element nodes when an intrinsic media element is created. Graph construction reads the internal prop-level metadata only when an intrinsic media element produces an Asset Entity.

The origin transport should use internal hidden-symbol metadata on Author Element nodes keyed by media source prop rather than changing the public `src` value shape or relying on an external WeakMap. This keeps media props serializable authoring strings while letting composition and graph construction carry per-prop Media Source Origin, such as `src` or `poster`, to the AssetLoader context. Prop-level metadata is required because `video.src` and `video.poster` on the same authoring node may come from different authoring modules after component prop forwarding.

The hidden metadata should live in a separate Author Element node metadata slot, such as a symbol-keyed map from prop name to Media Source Origin, rather than being mixed into the `props` object. `AuthorElementProps` remains serializable authoring data for validation and inspection, while graph construction can read the hidden metadata when creating Asset Entities.

The hidden-symbol metadata writer should stay internal in v0.8.5. It should not be exported from the root `deckjsx` package, from a speculative `deckjsx/integration` subpath, or as an ordinary authoring helper. v0.8.5 core tests may use internal helpers to validate prop-level metadata transport. A plugin-facing subpath should be introduced in v0.9.0 alongside the actual `@deckjsx/vite` implementation, when the minimum integration contract is known.

The initial Media Source Origin metadata scope is limited to authoring media source props whose values need module-relative interpretation: `img.src`, `video.src`, and `video.poster`. Inline media data props such as `data` and `posterData` still produce Asset Entities and Asset Source Fields, but they do not need Media Source Origin. Style-owned assets should wait until they are formally connected to the Asset Loading Boundary.

The Asset Entity should retain which media prop produced it, such as `sourceField: "src"` or `sourceField: "poster"`, separately from Media Source Origin. The source field is useful for diagnostics and inspection, but the origin itself remains the module/source identity used to interpret relative media sources. `sourceField` is required on Asset Entity and uses a core-owned vocabulary: v0.8.5 supports `src`, `data`, `poster`, and `posterData`; future style-owned asset fields should be added deliberately by core rather than accepted as plugin-defined strings.

The Vite default AssetLoader should resolve relative/path sources with Media Source Origin, then return core AssetLoader results: `probe()` returns media type, extension, dimensions when needed, byte length, and content hash when available; `load()` returns `Uint8Array` bytes. It should not only rewrite media references to public URLs, because PPTX output needs embedded media bytes and core should reuse those bytes through Asset Artifacts rather than re-fetching them later.

Within `@deckjsx/vite`, path semantics should follow Vite expectations rather than deckjsx-specific rules. Relative media paths resolve from Media Source Origin through Vite's resolver and module graph. Root-absolute paths such as `/logo.png` should be interpreted through the Vite project model, including public-directory behavior where appropriate, because slide authors are likely to use Vite's `public` asset convention.

Specifically, `@deckjsx/vite` treats `/asset.png` as a Vite public-root asset and returns embedded-media bytes through the AssetLoader. Core `deckjsx` does not special-case a leading slash; outside an integration package it remains an authored path source that requires a loader.

`@deckjsx/vite` should use loader diagnostics for resolver, public-directory, media-type, dimension, and file-read failures so those failures appear in Project Result or Render Result diagnostics. Returning `undefined` from a loader should mean "this loader does not handle this source"; handled-but-failed sources should be represented as Asset Loading Boundary diagnostics rather than silently falling through to a generic missing-loader failure.

Future loader result typing should model this as an async Result-like outcome returned by both `probe()` and `load()`, not as a custom Promise extension. The Promise resolves to either `{ ok: true, value, diagnostics? }`, `{ ok: false, diagnostics }`, or `undefined` for not-handled. Failure `diagnostics` should be `readonly Diagnostic[]`, not the aggregate `Diagnostics` result type; Project and Render wrap those diagnostic items into stage diagnostics when integrating the outcome. `AssetProbeResult` and `AssetLoadResult` are success-value shapes and should not carry their own diagnostics fields; success warnings and failed errors belong to the surrounding outcome. Failed diagnostics must include at least one error diagnostic; empty or warning-only failed diagnostics are invalid outcomes because a Result-like failed case should be blocking and explain itself. Warning-only diagnostics belong on successful handled outcomes. A handled failed result means the loader owns the source and Project or Render should stop resolving that source and surface the diagnostics instead of trying later loaders or the built-in resolver. Throwing should be reserved for unexpected loader execution failures, because deckjsx should prefer diagnostics for expected user-manageable project asset problems.

The Vite loader should also provide a stable Resolver Identity for Asset Artifact cache keys. An identity based only on loader display name or registration index is not enough for project integration because the same authored path can resolve differently under different Vite roots, aliases, public directories, or plugin graphs. Resolver Identity is integration-owned metadata, not an authoring option.

v0.8.5 should replace the current `scope` vocabulary in the AssetLoader contract with a required `resolverIdentity` field rather than keeping compatibility aliases. The current `name` fallback and anonymous registration-index fallback should be removed. deckjsx is still before the HMR-oriented compatibility line, and preserving multiple identity names would create avoidable contract debt.

Built-in multi-runtime asset handling should use the fixed Resolver Identity `deckjsx:builtin`. Built-in URL fetching may still produce different bytes in different runtime environments, but v0.8.5 should explain that through Asset Resolution Provenance and diagnostics rather than creating environment-specific built-in identities.

For `@deckjsx/vite`, Resolver Identity should be scoped to the Vite project instance plus resolver-affecting configuration fingerprint. At minimum it should distinguish project root, public directory, base, relevant resolve aliases, and the plugin/resolver graph that can affect asset resolution. An initial stable identity string can be shaped like `@deckjsx/vite:{root}:{configFingerprint}` as long as the fingerprint changes when asset resolution assumptions change.

Asset loader results should also be able to carry runtime-neutral Asset Resolution Provenance. `@deckjsx/vite` can use provenance kinds such as file, public asset, or generated asset to explain whether bytes came from an ordinary resolved file, Vite public-directory lookup, or plugin-generated asset. Core should store and expose that provenance for diagnostics, inspection, cache explanation, and future HMR without depending on Vite module graph objects or Node file handles.

Asset Resolution Provenance belongs in inspection and explanation surfaces, such as `deckjsx/inspect`, not in the everyday root Authoring Interface. Authors keep writing `src` and `data`; tools can inspect provenance when debugging asset resolution or HMR behavior.

Project inspection should expose asset resolution through a separate lightweight summary field, `assetResolutions`, rather than mixing it into the existing PPTX media summary. Asset resolution happens before PPTX media part projection and must also explain assets whose probe failed or whose source never became a media part. The summary should include identifiers and explanation fields such as asset entity id, source kind, source field, Resolver Identity, provenance kind, resolved id, importer, hash source, and diagnostic codes, but it should not expose loaded bytes or raw authored source payloads.

The initial provenance kind vocabulary is closed and core-owned: `inline`, `fetch`, `file`, `publicAsset`, and `generatedAsset`. Authored `bytes` and `data:` sources both map to `inline`; built-in URL retrieval maps to `fetch`; ordinary resolved files map to `file`; Vite public-directory assets map to `publicAsset`; plugin-created virtual or generated assets map to `generatedAsset`. `@deckjsx/vite` should map Vite-specific behavior into those kinds and attach resolver details separately, rather than introducing plugin-defined provenance kinds.

Provenance should use strongly typed scalar fields, such as resolver identity, optional resolved id, optional importer, and hash source. `resolvedId` and `importer` are strings. Provenance should not include Vite module graph nodes, URL objects, filesystem handles, an open `details` bag, or plugin-defined objects. If future integrations need more provenance data, the core provenance vocabulary should grow deliberately.

Asset Resolution Provenance should normally be carried by `AssetProbeResult` so Project Result can explain asset resolution before Render. `AssetArtifact` should preserve the probe provenance, and `load()` may preserve or refine provenance when byte-level explanation is only available after reading bytes.

The canonical content hash remains `AssetProbeResult.hash`, because existing media allocation and cache behavior can already use it. Provenance may record how the hash was obtained, but should not carry a second hash value that could drift from `AssetProbeResult.hash`.

The initial provenance hash source vocabulary is `loader` or `bytes`. Metadata-derived hashes, such as mtime-like file metadata, should not be placed in `AssetProbeResult.hash` or provenance hash source until deckjsx gives them explicit semantics, because media allocation should prefer content-equivalent hashes.

The intended release phasing is to use v0.8.5 as a pre-v0.9.0 core seam release: it should prepare the internal connection points and data flow that the v0.9.0 Vite plugin will use directly, including Media Source Origin transport, asset loader outcome typing, resolver identity, Asset Resolution Provenance, Integration Context plumbing, and inspection exposure. v0.8.4 remains available for separate table-tag and PowerPoint compatibility work. The v0.9.0 line can then introduce the monorepo `plugins/vite` package and its Vite-aware default AssetLoader on top of the v0.8.5 core seams rather than redesigning the boundary.

The v0.8.5 core work should be testable without the Vite plugin. Core tests should be able to attach Media Source Origin to `img.src`, `video.src`, and `video.poster`, pass that origin to a custom AssetLoader, surface handled-failure diagnostics in Project Result or Render Result, and preserve Asset Resolution Provenance for inspection. This keeps v0.9.0 focused on Vite resolver behavior rather than unresolved core pipeline mechanics.

Because v0.8.5 removes root `Deck.useAssets` and does not expose speculative AssetLoader types from the root package, custom loaders for v0.8.5 tests should be injected through internal pipeline seams such as `projectSource`, `renderSource`, or an internal Integration Context helper, not through public authoring APIs.

The v0.8.5 core seam is best implemented as one cohesive slice rather than split into a pure-type propagation PR and a later hidden-metadata PR. The slice should include the hidden-symbol Media Source Origin transport, internal Integration Context plumbing, loader outcome typing, AssetLoader context origin, resolver identity, provenance propagation, diagnostics, and inspection tests together so the connection can be validated end to end before the Vite plugin exists.

The public surface for v0.8.5 should stay narrow. Root `deckjsx` should not expose AssetLoader contracts, loader outcome types, provenance types, Asset Source types, or hidden-symbol media-origin helpers speculatively. This means removing root exports such as `AssetLoader`, `AssetLoaderContext`, `AssetProbeResult`, `AssetLoadResult`, and `AssetSource` along with removing `Deck.useAssets`. Those contracts can remain internal until `@deckjsx/vite` or another integration package needs a stable plugin-facing subpath such as `deckjsx/integration`. Detailed provenance inspection models may be exposed through `deckjsx/inspect` only when they are reader-facing inspection data rather than integration hooks.

v0.8.5 is complete when the core seam satisfies these checks:

- core `deckjsx` does not add new `node:*` imports
- `src` and `poster` remain authoring-facing strings
- hidden-symbol metadata can carry Media Source Origin for `img.src`, `video.src`, and `video.poster`
- prop-passed media paths retain the module origin that authored the path value
- internal Integration Context can provide default AssetLoaders without root authoring registration
- `AssetLoaderContext` carries source, optional origin, Resolver Identity, Asset Entity id, and Asset Source Field
- `probe()` and `load()` distinguish success, handled failure, and not-handled outcomes
- handled-failure diagnostics surface through Project Result or Render Result
- root `Deck` no longer exposes manual `useAssets` registration
- root `deckjsx` no longer exports speculative AssetLoader contract/source/result types
- core Render no longer accepts `output: string`, performs Node file writing, or exports Node output side-effect types
- Asset Resolution Provenance is available from Project-time inspection
- provenance kind is limited to `inline`, `fetch`, `file`, `publicAsset`, and `generatedAsset`
- `AssetProbeResult.hash` remains the canonical content hash, while provenance records only `hashSource` as `loader` or `bytes`

The hidden-symbol Media Source Origin writer should remain internal or plugin-facing rather than becoming a root public authoring helper. v0.8.5 core tests may use internal helpers to validate transport, and v0.9.0 can expose an appropriate integration-facing path for `@deckjsx/vite`, but ordinary users should not need to call a `withMediaOrigin`-style API.

The initial `@deckjsx/vite` public surface should be a Vite plugin factory, shaped like `deckjsx()`, for use in Vite config. The plugin owns transform setup and default AssetLoader registration. Lower-level loader factories or sub-entries, such as a hypothetical `@deckjsx/vite/loader`, should stay internal until a concrete external use case needs them.

The Vite integration should automatically provide its default AssetLoader instead of asking authors to call `deck.useAssets(...)`. v0.8.5 should remove root `Deck.useAssets` manual registration rather than preserving it as a compatibility escape hatch. This revises the v0.8.0-era assumption that authors normally configure asset loading by calling `deck.useAssets(loader)`.

Automatic loader installation should be module/source scoped rather than process-global. `@deckjsx/vite` should use transforms to inject or connect an Integration Context for deck modules; that context can provide the default AssetLoader and Media Source Origin writer to Deck/source registration without requiring user-authored loader registration calls. Avoid a global singleton registry because multiple Vite dev servers, tests, monorepos, and HMR sessions can coexist with different resolver assumptions.

When decks or sources are composed, the pipeline should aggregate the Integration Contexts contributed by each source instead of treating the parent Deck's context as the one context for the whole graph. This lets a mounted source keep the resolver assumptions attached by the module or project integration that authored it. Asset Entity Media Source Origin remains the per-asset explanation of where a media value came from; Integration Context supplies the source/module-scoped loader assumptions used to interpret those origins.

Asset resolution should use the Asset Entity's owning Integration Context rather than trying every loader from every composed source. This prevents a parent Vite project root, alias set, or public directory from accidentally claiming a child source's relative asset. Built-in runtime-neutral handling may still apply to inline data and fetchable absolute URLs when no project-local loader claim is involved, but project-local paths should not fall through across unrelated Integration Contexts.

Asset Entity should store only an opaque scalar reference to its owning Integration Context, such as an internal `integrationContextId`, not the Integration Context object or loader functions themselves. Project and Render can resolve that id against the aggregated Integration Context registry for the composed graph. An Asset Entity without an Integration Context reference can still use runtime-neutral built-in handling for inline data and fetchable absolute URLs, but project-local path sources without an owning context should fail through diagnostics rather than being guessed by another context.

`integrationContextId` and `resolverIdentity` are separate identities. `integrationContextId` selects the source/module-scoped Integration Context whose loader set may handle an Asset Entity. `resolverIdentity` identifies the resolver assumptions that produced an Asset Artifact and belongs in cache keys, provenance, and inspection. For `@deckjsx/vite`, the Integration Context id can be module/source-context scoped, while Resolver Identity should be scoped to the Vite root, config, public directory, aliases, and resolver/plugin fingerprint.

When a filesystem-like path source has no owning Integration Context, Compile should still accept the authored media source. Project should report an Asset Loading Boundary error diagnostic, shaped like `E_PROJECT_ASSET_CONTEXT_MISSING`, because the path is syntactically valid but cannot be interpreted by core. Render should then stop through the normal Project-error path and return no artifact.

The Vite plugin should let users configure transform targets with `include` and `exclude` patterns, such as `include: ["src/**/*.tsx"]`. The plugin can default to JSX/TSX-like modules while excluding dependency directories, but it should not rely only on detecting `Deck` usage. Transforming a matched module should still be cheap and no-op when no deckjsx media-origin work is needed.

The initial default transform target should include `**/*.{jsx,tsx}` and exclude dependency directories such as `node_modules/**`. Projects that want narrower behavior can configure `include`, for example `include: ["src/slides/**/*.tsx"]`.
